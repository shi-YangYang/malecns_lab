## 1. 已确认的 Adam 缺口

当前 [`_audited_gradient_update`](../../src/malecns_lab/learning/x2_behavior_training.py)（469–573行）先保存原始梯度与参数，拒绝非有限 loss/梯度，执行 Adam 后检查参数。原始梯度安全平方与 Adam 状态有限性只在 `check_adam_scale=True` 时检查；worker 的686–693行只为 `probe-stabilized` 开启该开关，`joint` 未开启。

**有限梯度与有限参数，不能推出有限 Adam 状态。** 本地安装的 PyTorch `torch/optim/adam.py` 的475行更新二阶矩，544–546行用二阶矩平方根作分母，再更新参数。举一个静态数值反例：float32 中有限的单坐标梯度约 `1e22`，fresh Adam 的二阶矩目标为 `0.001 × (1e22)^2 ≈ 1e41`，超过 float32 最大值约 `3.4028e38`；一阶矩仍可有限，分母为 `inf` 时该坐标增量可以为0，原参数保持有限。后续更新仍会带着该非有限二阶状态继续。该推导不是本次实际 MPS 复现，也没有声称现有 run 已出现该故障。

第二探针实测最大 theta 梯度 `4.76142895104e11` 尚远小于安全平方界 `sqrt(float32_max) ≈ 1.84467435e19`，其一次 Adam 状态已有限。它证明那个片段可更新，不能保证其他任务、后续状态或多次更新的梯度仍在界内。不能把“大梯度”本身误写成已经发生 Adam 溢出。

现有最终 `restore_checkpoint`（399–419行）会核对所有归档数组，包括已保存的 optimizer 数组。因此，若二阶矩一直为 `inf`，最终候选恢复通常仍会拒绝，**缺口是逐步更新的及时准入、失败定位及证据，不是现有代码必然会把含非有限 Adam 状态的最终 run 宣布成功**。在末尾才失败之前，多个更新审计可已标成 `completed`，并浪费完整脑训练与验证预算。

### 最小准入修复要求

仅修改训练审计器和其模式调用，不改变脑、编码、头、损失或优化器数值算法：

1. 联合模式的每一次更新都检查原始梯度安全平方；沿用当前保守界，不裁剪、缩放或替换梯度。非有限或超界时先保存原始证据，拒绝 `optimizer.step()`，实际完成更新数不增加。
2. 将“fresh Adam 是第一次探针的要求”与“本次梯度/状态可准入”拆开。当前544行强制 `fresh_optimizer`，不能简单把 `joint` 的开关改成 True，否则正常第二步也会被拒绝。探针继续要求 fresh；joint 第一步 fresh、后续步允许已有状态。
3. 每次 step 前核对已有 Adam tensor 状态有限；step 后在接受这次更新前核对所有 Adam tensor 状态有限，同时保留已有参数校验。状态不是梯度，不能仅用梯度的 `max_abs` 代替检查。已有有限状态与保守平方界降低风险，step 后检查仍是对实际算子结果的必要确认。
4. 审计持久化更新前后状态的有限性、非有限计数和相关原始数组；至少失败路径保留实际 Adam 状态，区分 `gradient_admission`、`optimizer_state_admission`、`optimizer_step`、`optimizer_state_validation`。若 step 已执行后才发现失败，实际计数和参数变化必须如实保留，立即结束整次 run，不回滚伪装“未更新”、重试、自动续训或改 LR/gain。

`gain=0.1`、loss scale=1、lr=0.001、betas=(0.9,0.999)、eps=1e-8、weight_decay=0、amsgrad=false 均不因该修复改变。无需为此添加全部50步边界梯度归档、改数据、改训练调度或重跑已通过的完整脑探针。

未来实现的定向验证限定为同一审计器的 CPU 小 fixture：连续两次安全更新能通过且第二次非 fresh；有限但超平方界梯度在 step 前拒绝；已污染状态在 step 前拒绝；step 后状态变坏但参数仍有限时能拒绝并保留真实计数/数组。已有探针拒绝用例可纳入同一次局部 pytest 调用，不运行全项目检查或完整脑。本文未执行这些测试；实施后由新的独立验收者审查一次检查结果，不机械重跑。

## 2. 200次更新实际上覆盖什么

[`select_episodes`](../../src/malecns_lab/learning/x2_behavior_training.py) 按 GREET、FACE_LEFT、FACE_RIGHT、SHOW_FORWARD、END_INTERACTION 任务轮转选择 episode。读出模式每次取一个**完整** episode 的缓存特征；joint 的814–844行每次只取该 episode 的**下两帧**，保存状态、更新参数并 detach，下次轮到它才接着推进，走完后才重置。跨窗口状态因此是在先前参数下得到的状态，下一窗口使用届时已更新的参数；这是当前截断训练语义，不是所有帧都由同一固定参数重算。

对本次相同50条训练元信息进行纯索引计数，结果如下；没有执行模型或读取模型分数：

| joint 更新数 | 实际处理帧次数 | 不同帧 / 416 | 至少完整走过一次的 episode / 50 | 600步预热次数 |
|---|---:|---:|---:|---:|
| 50 | 100 | 100 | 0 | 50 |
| 100 | 184 | 184 | 18 | 50 |
| 150 | 284 | 248 | 24 | 68 |
| 200 | 367 | 299 | 27 | 74 |

200次时每个 episode 被访问4次，但短序列已经重开，长序列只走到第8帧以内：

| 任务 | 不同帧 / 该任务总帧 | 完整 episode / 10 |
|---|---:|---:|
| GREET | 61 / 64 | 9 |
| FACE_LEFT | 68 / 105 | 3 |
| FACE_RIGHT | 68 / 105 | 3 |
| SHOW_FORWARD | 70 / 110 | 2 |
| END_INTERACTION | 32 / 32 | 10 |

SHOW_FORWARD 完整的两条只是 rejected/missing_feedback；LEFT/RIGHT 另外完整的是 already_aligned。正常转向/前进后的挥手和收尾仍有大量尾帧未训练。**200次 joint 不能写成“50条完整序列训练4轮”。** 本次50条每条完整走一次理论至少需要225个两帧窗口；按当前固定轮转、不跳过已完成短序列的调度，最长18帧片段到第9轮才走完，所有50条首次完整的精确位置为第429次更新（最后是SHOW_FORWARD/switch_request），若跑完第9整轮则为450次。均超过现有200次上限，不可暗中放宽。

默认 joint 的4次更新甚至只访问前4个任务，缺 END，且都是 rejected 开头；默认5条训练/验证也只含 rejected，不能拿默认参数声称覆盖主线。减少 episode 前缀会丢掉后续情境，不应为了获得“完整覆盖”的表述而静默缩小训练范围。若将来需要一次完整覆盖，必须单独登记调度/预算方案；本次最小 Adam 修复不兼做调度重构。

### 40条完整episode、逐条连续推进的替代方案

按同一task-round-robin的**前40条**，恰好每任务8条、8类context各一条：rejected、missing_feedback、waiting_stand、already_aligned、repeat_request、switch_request、slow_feedback、normal。它保留全部五任务和八类情境，减少的是每任务额外两条normal参数家族；相比50条覆盖范围缩小必须明确，不是相同数据量实验。

| 任务 | 完整帧数 | 两帧窗口更新数 |
|---|---:|---:|
| GREET | 51 | 27 |
| FACE_LEFT | 81 | 43 |
| FACE_RIGHT | 81 | 43 |
| SHOW_FORWARD | 86 | 46 |
| END_INTERACTION | 26 | 16 |
| 合计 | 325 | 175 |

替代调度为：保持40条episode的既定顺序；一条episode仅初始预热一次，依次推进两帧窗口、反向更新、detach，直至包含最后一帧，再重置进入下一条。**175次更新恰好完整一遍**，其中150个双帧窗口、25个单帧尾窗、40次600步预热；保留现有200次更新封顶即可。验证仍为与基线相同的全部50条/402帧，不挑简单验证子集。头仍仅取神经特征；不改教师、图、码本或窗口内信用。

当前成本证据仍不足以准入7200秒：

- 本次基线在读取快照时已归档全部416训练帧。50条中366个同episode相邻帧间隔均值为 **5.583621秒**，中位5.605601秒，最小5.198412秒、最大7.310452秒；含前向/归档，不是纯模型耗时。首帧至末帧共2630.558583秒；跨episode的49个间隔扣除一帧均值后，估计每次预热及边界附加成本约6.395018秒。据此估计50条/402帧验证缓存约 `402×5.583621 + 50×6.395018 = 2564.37秒`。当时实际validation仅开始，故这仍须由其最终真实耗时替换。
- r2 `mps_memory.csv` 的阶段采样可拆为图/初始化到precondition约3.347038秒、600步预热6.379768秒、两帧前向至完成约 **27.728982秒**。后一个数字含反向、边界审计、更新、归档及收尾，不是净Adam耗时；probe只对第二帧施加loss，而joint对窗口帧平均loss，二者不是等价速度基准。
- 若175个窗口都按27.728982秒计，训练约4852.57秒，加40次预热约255.19秒、加载约3.35秒、验证约2564.37秒，合计约 **7675.48秒**。即使把25个单帧尾窗粗略按半价折算（325/2个双帧等效窗），仍约 **7328.86秒**。两者都尚未加15%余量；含余量约 **8428–8827秒**，已经超过现7200秒硬上限。
- 逐episode推进可能少保留并行状态，joint又没有probe的全部边界梯度归档，因此实际可能更快；反向成本、输入活动、状态归档也可能更慢。不能把未测优化收益当预算依据。在固定50条验证估计下，要含15%余量地完成175次更新，平均每窗（含单帧尾窗）约须≤19.65秒；当前没有该联合吞吐证据。

所以**40条方案的样本/更新覆盖成立，当前时间准入不成立**。不在7200秒上限下硬启动并期待省出时间，不自动增预算，也不以少看正常尾部、减少验证或打开locked-test凑出可完成方案。协调者已明确：等待基线完成后，用实际结果另定一次40条/175窗口登记；必要时仅为该新joint登记将墙钟上限设为 **9000秒**，依据是当前估计加15%余量，readout/evaluate上限不变。9000秒目前只是待最终成本确认、实施与独立准入的有限方案，不是当前执行授权或无限续训。本轮不实施调度、不改当前run。

## 4. 只改训练审计器是否改变模型身份

**只改 `learning/x2_behavior_training.py` 的训练审计与模式接线，不改policy/brain/encoder/data，当前模型policy身份不会因此改变。** `X2BehaviorPolicy` 的118–137行绑定完整图、输入映射、头契约、初始化、policy自身源码、MPS数值源码、固定反向身份与运行库版本；其中不含训练审计器源码。`brain/mps_identity.py` 的model identity仅绑定列出的brain文件。训练代码的 `source_inventory` 则明确包含训练审计器并递归登记本地依赖，因此**新run的源码清单与registration_id会变化**，不能声称使用了和读出 run 相同的训练实现。

这不需要放宽checkpoint恢复或伪造迁移。worker仍先用同一旧theta初始化定义、相同seed/gain与当前未变policy源码构造同一policy身份，再通过完整 `meta["policy"] == policy.identity` 检查，精确复制本次选中checkpoint的theta及三头参数，建立新优化器。旧checkpoint中的原registration/context继续保留，新run登记其路径和元数据/数组hash；未来参数改变生成新checkpoint ID，不能覆盖旧checkpoint或旧source快照。

若实现顺手修改了policy、brain、encoder、初始化或依赖版本，以上“身份不变”结论不再成立；即使仅是注释导致源码hash变化，也不能绕过严格恢复。那将需要明确的新身份/迁移方案，超出本次最小修复。正在运行的读出会在结束时复核所有登记源码，所以**任何训练审计器修改也必须等它真正退出后再做**。
